Two deployment methods

GitHub Actions is recommended for the first deployment. Use Wrangler CLI once you are familiar with it. Both methods deploy the same full-stack Worker application.

What the one-click deployment does

The project’s existing backend-deploy.yml calls _deploy-cloudflare.yml: validate variables → install frontend/backend dependencies → run security/contract tests → build Vue → resolve/create D1 and KV → safely generate wrangler-ci.toml → atomically apply Worker secrets → deploy → call /api/health → use X-Init-Secret to run idempotent database initialization/migrations.

Run Backend first

Deploy backend to Cloudflare with initialize_database=true. Meanwhile, Deploy frontend to Cloudflare also redeploys the same Worker + Assets, but does not call the database initialization endpoint, making it suitable for frontend-only updates.

Note:Actions automatically creates missing D1 and KV resources, butdoes not automatically create an R2 bucket. If you set R2_BUCKET_NAME, create that bucket first in the Cloudflare Dashboard or with Wrangler.

Create a Cloudflare API Token

The workflow needs permission to deploy Workers and create/read KV and D1. Custom domains and R2 require their corresponding permissions. Scope the token to only your Cloudflare Account / Zone.

Recommended permissions for the current workflow:
Account · Workers Scripts · Edit
Account · Workers KV Storage · Edit
Account · D1 · Edit
Account · Workers R2 Storage · Edit      # only when using R2
Zone    · Workers Routes · Edit          # when using CUSTOM_DOMAIN

Log in to Cloudflare and create required resources

D1 and KV are hard requirements for the current Worker. R2 is optional; without R2, the attachment layer falls back to KV, and external S3 can also be configured in admin settings.

pnpm wrangler login

# Required
pnpm wrangler d1 create cloud-mail
pnpm wrangler kv namespace create cloud-mail

# Optional; recommended for larger attachment workloads
pnpm wrangler r2 bucket create cloud-mail-assets

Initialize / migrate the database

The Worker exposes an idempotent initialization endpoint protected by init_secret ; the first GitHub Actions backend deploy uses the same mechanism rather than executing a fixed SQL file.

BASE_URL="https://cloud-mail.YOUR_SUBDOMAIN.workers.dev"

curl -fsS "$BASE_URL/api/health"

curl -fsS -X POST \
  -H "X-Init-Secret: $INIT_SECRET" \
  -H "Accept: text/plain" \
  "$BASE_URL/api/init"

# Expected response: success
Do not deploy INIT_SECRET in a public URL. The project retains a compatibility GET /init/:secret, but production deployments should use POST /api/init + X-Init-Secret。

Deployed ≠ ready to receive email

The Worker exports an email(message, env, ctx) handler, but Cloudflare still needs to route your mail domain to this Worker.

Manual setup required

1 · Onboard your mail domain

In Cloudflare Email Service / Email Routing, onboard every domain in the DOMAIN array. The domain must use Cloudflare DNS; Cloudflare configures the MX and related records required for receiving mail.

2 · Route mail to the cloud-mail Worker

Recommended: Catch-all → Send to a Worker → select the deployed Worker (default name cloud-mail). CloudMail then decides whether to accept or reject mail based on recipient address, account state, and role permissions.

Do not confuse the two domain settings:DOMAIN=["example.com"] is the domain allowed in mailbox addresses;CUSTOM_DOMAIN=mail.example.com is the Web/API access hostname. They serve different purposes. Do not set mail.example.com as the only mail domain unless you actually want addresses like user@mail.example.com。

Inbound email

Email Routing → Worker email() → PostalMime → D1 + object storage → iOS/Web.

Internal delivery

Recipients on the same CloudMail internal domains can be delivered directly without an external sending service.

External delivery

Requires Cloudflare send_email binding, or a Resend Token configured for the sender domain in system settings. Without either option, the project intentionally rejects external delivery.

First initialization and administrator

Database initialization creates tables, migrations, default roles/permissions/settings only. It does not pre-create an administrator password.

Check health status

Run database init

The GitHub Backend workflow does this automatically. With CLI deployment, run it once. You may call it again after upgrades; migrations advance by project version and are designed to be repeatable.

Register the administrator account

Open the Worker URL / CUSTOM_DOMAIN and register with the email address that ADMIN exactly matchesand set your own password. The backend uses env.admin to identify the administrator instead of creating a hard-coded admin user during init.

Optional capabilities

These are not required for core inbound mail, but are natively supported by the project.

R2 / S3 attachment storage

Object storage is selected at runtime: use S3 when full S3 settings are configured; otherwise, if an r2 binding exists, use R2; otherwise fall back to KV. R2 or S3 is recommended for large or long-lived attachments.

CF Mail iOS Push Gateway

The self-hosted Worker does not store Apple APNs device tokens or keys. It stores only the scoped subscriptionId + pushSecret issued by the Gateway.CFMAIL_PUSH_GATEWAY_URL is empty, the code defaults to the official Gateway; set it to disabled to disable it explicitly.

Cloudflare Email native outbound

Set CF_EMAIL=true in the GitHub workflow and it generates [[send_email]] name="email". This binding handles outbound email only and does not replace inbound Email Routing rules.

Custom access domain

Set CUSTOM_DOMAIN=mail.example.com and CI generates [[routes]] custom_domain=true; workers.dev is still retained so initialization can try workers.dev first and then fall back to the custom domain.

Common troubleshooting

The cases below are based directly on error branches in the source code and deployment workflow behavior.

/api/health is 200 but ready=false
Check checks：d1=false → missing db binding；kv=false → missing kv binding；jwtSecret/initSecret=false → secret missing or shorter than 32 characters.
Login says “D1 database not bound / KV database not bound”
Binding names cannot be renamed to DB, KV1, etc. The project reads c.env.db and c.env.kv。
Web UI loads, but API is 404 / requests hit the wrong host
Confirm you are using the release build.mail-vue/.env.release sets VITE_BASE_URL=/api , and outputs to ../mail-worker/dist. The page and API should share the same Worker origin.
Deployment succeeds but no mailbox receives mail
Check Cloudflare Email Routing: mail domain onboarding, MX records, and whether Catch-all/specific rules use Action=Send to a Worker and point to this Worker. Worker deployment does not create Email Routing rules automatically.
Internal mail works but external recipients fail
This is intentional protection: external delivery requires env.email(Cloudflare send_email binding) or a Resend Token configured for that sender domain.
Actions deployment fails after setting R2_BUCKET_NAME
The current Actions workflow only binds the R2 bucket you specify; it does not run wrangler r2 bucket create. Create the bucket first, or remove the variable temporarily to use the KV fallback.
POST /api/init returns 401 / 503
401 means X-Init-Secret does not match the Worker secret;503 means init_secret is missing or too short. Incorrect secret attempts also trigger IP rate limiting, so do not repeatedly guess.
init returns 404 immediately after custom-domain deployment
Custom Domain propagation may take time. The GitHub workflow first extracts the workers.dev URL from Wrangler logs and retries initialization across workers.dev and CUSTOM_DOMAIN.
