CloudMail Cloudflare Deployment Guide

Deploy mail-vue and mail-worker from the repository that owns the workflow. No cross-repository checkout or extra source-repository token is required.

Architecture

Browser
  ↓
CloudMail Worker + Vue Assets
  ├─ D1 (required)
  ├─ Workers KV (required)
  ├─ R2 / external S3 (optional)
  ├─ Cloudflare Email Routing
  ├─ Resend / send_email (outbound)
  └─ optional hosted notification URL

mail-vue builds into mail-worker/dist. Worker code and Web assets are deployed together.

One workflow

.github/workflows/cloudflare-deploy.yml

verify

Tests and production build only.

deploy

Tests, build and deploy Worker + Web assets.

deploy-and-migrate

Deploy, protected init, then versioned D1 migrations.

Pushes and pull requests validate only. Start production deployment manually from GitHub Actions.

Required Actions secrets

NamePurpose
CLOUDFLARE_API_TOKENCloudflare API access for Workers/resources.
CLOUDFLARE_ACCOUNT_IDCloudflare account ID.
JWT_SECRETJWT signing secret, at least 32 characters.
INIT_SECRETProtected initialization secret, at least 32 characters.
CONFIG_ENCRYPTION_KEYDynamic configuration encryption root key, at least 32 characters.
Important: the three application secrets must be different values and must never be committed to the repository.

Email Routing

  1. Enable Cloudflare Email Routing for every receiving domain.
  2. Complete Cloudflare's MX/DNS requirements.
  3. Create a Catch-all or specific address rule.
  4. Choose Send to a Worker.
  5. Select the deployed CloudMail Worker.
  6. Keep the DOMAIN variable aligned with the routing domains.

Deploying the Worker alone does not create inbound routing rules.

First production deployment

  1. Configure Secrets and Variables.
  2. Run deploy-and-migrate.
  3. Wait for Worker deployment, protected initialization and migrations to complete.
  4. Verify /api/health.
  5. Configure Email Routing and test inbound/outbound mail.
curl -fsS https://mail.example.com/api/health

Ready for production when the response contains "ready": true.

Optional hosted notifications

The Worker can submit supported events to:

https://push.readori.com

To disable the optional integration:

CFMAIL_PUSH_GATEWAY_URL=disabled

Core Web, API and mail functionality continues to work without hosted notifications. The service implementation is outside the public self-hosting source scope.

Common troubleshooting

Deployment succeeds but no inbound mail arrives

Recheck Email Routing, MX/DNS and the rule that sends mail to this Worker.

External recipients fail

Configure Resend or Cloudflare outbound email. External sending requires an outbound provider.

/api/health is not ready

Check D1, KV, required secrets and initialization/migrations. For first deployment or schema changes, run deploy-and-migrate.

R2 binding fails

Create the bucket before setting R2_BUCKET_NAME, or remove that variable.
